# AR Try-on: whole-app audit — 2026-09-26

**Scope:** everything that ships. That's the embedded admin (`apps/shopify-app/app`), the public server routes, the theme app extension (`extensions/tryon-button`), the storefront try-on engine (`main.js`, `src/`, built to `public/tryon`), billing, privacy/GDPR, and engineering health.
**Method:** source review, plus running the repo's own gates:
- `apps/shopify-app`: 401 tests pass against a local Postgres.
- Engine (repo root): 192 tests pass.
- Root `npm run typecheck`: fails (93 errors).
- `npm run validate` and `npm run validate:tryon`: both crash.

Nothing was exercised in a live store. This environment has no authenticated Shopify session, and its network policy blocks `cdn.shopify.com`.

The admin's UI/UX has its own audit in [`polaris-audit-2026-09-25.md`](polaris-audit-2026-09-25.md) (22/24). It isn't repeated here.

## Fix status

**Fixed:**
- **#1:** the iframe has no `src` until the shopper opens the try-on, and the dialog's `close` event resets it to `about:blank`, which unloads the engine and releases the camera. The engine also destroys itself on `pagehide`.
- **#2:**
  - `src/tryon/remoteConfig.js` makes a config failure an error the page shows ("isn't available", or retry for 503 and network faults), never the bundled demo frame, whenever a shop and product are present.
  - On a lapse, the subscription webhook writes the grace end to an app-data metafield (`app.metafields.tryon.serve_until`), and clears it on reactivation. The block hides the button after that time and explains why in the theme editor.
- **#3:** scopes are now `write_products` only.
- **#4:** the MediaPipe wasm (copied from `node_modules` by `scripts/copy-mediapipe.mjs`) and the face model (`public/mediapipe/`) are served from `/tryon/mediapipe/`. The privacy policy now describes exactly what a shopper's browser downloads and from where.

**Still open:** #5–#18.

## What's already right (keep it)

- **SSRF-proof model fetching.** The code allowlists a single host (`cdn.shopify.com`) by exact match, rejects credentials and ports, sets `redirect: 'error'`, counts decoded bytes against the size cap, and applies a timeout (`remoteGlb.server.js`).
- **GDPR done carefully.** `purgeShopData` deletes storage before rows so a failed purge can be retried, and it refuses an empty `shop`, which would otherwise delete every tenant. Uninstall and redact are kept separate, and all three compliance topics are declared correctly under `compliance_topics`.
- **Billing fails closed.** An unknown plan name gets a product limit of 0, and the storefront never falls open to "servable" on a database error.
- **Honest error semantics.** The storefront config returns 503 plus `Retry-After` for database trouble, never a 404 that reads as "no try-on". Merchant-facing errors never forward raw exception text (with one exception, below).
- **Storefront cost stays low until used.** The engine iframe is `loading="lazy"` inside a closed `<dialog>`, so product pages pay nothing until a shopper taps Try on. Duplicate blocks on a template stand down to one.
- **Tests.** About 590 tests, including forced-failure and cross-shop checks.

## P1: fix first

### 1. The camera keeps running after the shopper closes the try-on
- **Where:** `tryon_button.liquid:95-97`, `src/tryon/providers/MediaPipeThreeProvider.js:16`, `main.js:292-294`.
- **What happens:** the close button calls `dialog.close()`, which only hides the dialog. The iframe, the engine and the `getUserMedia` stream keep running. The camera tracks are stopped only on `beforeunload`, i.e. when the shopper leaves the product page.
- **Why it matters:** the browser's camera indicator stays on. The privacy policy (`privacy.jsx`) promises "When you close the try-on view, the camera stops." That's a trust problem, and a review risk for a camera app.
- **Fix:** on the dialog's `close` event, tear the engine down. Either reset the iframe (`frame.src = 'about:blank'` on close, restore on open), or `postMessage` a stop command the engine answers by calling `destroy()`. The first is simpler and guaranteed; the cost is re-initialising on reopen.

### 2. Any config failure shows the shopper different glasses than the product
- **Where:** `main.js:36-67`, `main.js:243`, `src/config/arConfig.js:199`.
- **What happens:**
  - `resolveRemoteSkuKey` catches every failure (402 lapsed subscription, 404 unmapped, 503 outage, bad payload) and falls back to `defaultGlassesKey = 'sunglasses'`, a bundled demo frame.
  - The shopper sees a working try-on of a product that isn't the one on the page.
  - For a lapsed shop it's worse. The storefront gate is the product metafield, and nothing clears it when a subscription lapses (`webhooks.app.subscriptions_update.jsx` only updates the row). So the button stays up indefinitely, and the paid feature degrades into a demo instead of switching off.
- **Fix:**
  - When `shop` and `productId` are present, never fall back to a bundled model. Show "Try-on isn't available for this product right now" (with Retry for 503).
  - After the grace period, stop the button showing. One option: unpublish the metafields when the grace period ends (a scheduled reconcile or the next admin load). Another: have the block read a shop-level "enabled" metafield the app owns.

### 3. Two access scopes are requested but never used
- **Where:** `shopify.app.toml:57`, `.env.example` (`SCOPES`).
- **What:** the app asks for `write_metaobjects` and `write_metaobject_definitions`, but no code touches metaobjects. The app only writes product metafields, which `write_products` covers.
- **Why it matters:** Shopify App Review rejects scopes that aren't demonstrably used, and the `.env.example` comment already warns about exactly this.
- **Fix:** drop both from the toml and `.env.example`. The scope change goes through `app/scopes_update` on existing installs.

### 4. The privacy policy leaves out two third parties that see every shopper
- **Where:** `src/tracking/FaceTracker.js:6-7`, `privacy.jsx` ("Service providers").
- **What:** the engine loads its face model from `storage.googleapis.com` and its MediaPipe WebAssembly from `cdn.jsdelivr.net`, both in the shopper's browser, so both receive shopper IP addresses and user agents. The policy lists only Vercel, Neon and AWS, and says no shopper data goes to any provider.
- **Fix:** self-host both files under `/tryon/` (also removes two external single points of failure), or disclose Google and jsDelivr in the policy. Self-hosting is the better fix.

## P2: important

### 5. A public endpoint lets anyone spend another shop's model quota and CPU
- **Where:** `api.register-model.jsx`, `models.server.js:117-181`.
- **What happens:**
  - The endpoint is unauthenticated. `shop` is caller-supplied and only checked for "is installed". The code's own comment says it doesn't prove the caller is that shop.
  - Anyone can register up to `MAX_MODELS_PER_SHOP` (50) distinct `cdn.shopify.com` GLBs under a victim shop. Any public store's files qualify. That runs a full calibration per request, and then locks the real merchant out with `QUOTA_EXCEEDED`.
  - It isn't billing-gated either.
- **Fix:** route the block's model override through an App Proxy (Shopify signs the request, proving the shop), or require the URL to belong to the named shop's own CDN path. Add a billing check and per-IP rate limiting.

### 6. Upload size is enforced only after the whole file is loaded
- **Where:** `storage.server.js:53-65` (presign), `models.server.js:45-60` (finalize).
- **What:**
  - The presigned PUT doesn't bind a content length, so the 25 MB cap is client-side only.
  - `finalizeUpload` reads the entire object into memory (`readModelGlb`) before checking its size. A holder of a presigned URL can upload gigabytes and make finalize exhaust the function's memory.
- **Fix:** use a presigned POST with a `content-length-range` condition, or `HEAD` the object and reject it by `ContentLength` before `GetObject`.

### 7. The storefront's config endpoint is uncached and writes on every request
- **Where:** `api.tryon-config.jsx`.
- **What:**
  - The response has no `Cache-Control`, despite comments calling this path "edge-cached". So every try-on open hits the database through a small connection pool; production has already seen pool timeouts (the comment on line 23).
  - It also calls `recordTryonSeen`, a throttled write, on every request. `api.tryon-installed` now provides the install signal that write was originally for.
- **Fix:** add `Cache-Control: public, s-maxage=60, stale-while-revalidate=600`, which is safe because mapping changes can lag a minute. Consider dropping `recordTryonSeen`, or moving it to the non-cached `tryon-installed` ping.

### 8. There's no CI, and two gates have rotted
- **What:**
  - There's no `.github/workflows`. The ~590 tests only run when someone remembers, which is how the `package-lock.json` drift went unnoticed until `npm ci` failed.
  - Root `npm run typecheck` fails with 93 errors.
  - `npm run validate` and `validate:tryon` crash (`import.meta.env.DEV` is undefined under Node).
  - The admin's `npm run typecheck` checks no app code, because `tsconfig.json` doesn't include `*.jsx` (already noted in `UI-REVIEW.md`).
- **Fix:**
  - Add a workflow: `npm ci`, a Postgres service, `prisma migrate deploy`, both test suites, lint and build.
  - Fix or delete the two validators.
  - Get the root typecheck green, or scope it until it can be.

### 9. Debug harness code ships in the production engine bundle
- **Where:** `src/core/RenderLoop.js:116-117, 259-350`, `MediaPipeThreeProvider.js:327-332`.
- **What:** the occlusion probe, the `window.__probe` and `window.__mock` hooks, and a helper that POSTs a composited camera frame to `/__shot` are all in `public/tryon/assets`. They're gated only by a `?probe=1` URL parameter.
- **Why it matters:** the storefront never sets that parameter, so this isn't an active leak. But code that uploads camera frames shouldn't exist in a build shipped to shoppers, and it weakens the "no frame ever leaves the device" guarantee.
- **Fix:** gate it on `import.meta.env.DEV` (as `resolveLocalFitKey` already is) so Vite strips it, and add the same grep-must-find-nothing check to CI.

### 10. There's no error monitoring
- **What:** all failure reporting is `console.error` or `console.log`. The pool-exhaustion 503s and any purge failures are only visible to someone reading Vercel logs.
- **Fix:** add an error tracker (e.g. Sentry) to the server and the engine, or at least a log drain with alerts on `compliance_webhook` failures and 5xx rates.

### 11. The storefront engine isn't accessible to screen-reader users
- **Where:** `index.html:16, 39`, `main.js:169-186, 201-235`.
- **What:**
  - `#loading` has no `role="status"` or `aria-live`, so "Preparing your try-on…" and every error are silent.
  - The whole scan overlay is `aria-hidden="true"`, so the instructions a shopper must follow ("Slowly turn your head left") are never announced.
- **Fix:** give `#loading` `role="status"` (use `role="alert"` for errors), and move the scan caption out of the hidden subtree into a polite live region.

## P3: polish

12. **Dead public route.** `models.$assetId.fit-preview[.]glb.jsx` composes a GLB on a mock head, which is CPU-heavy and unauthenticated. The UI stopped using it (its own comment in `ModelFitReview.jsx` says so). Delete it along with `fitPreview.server.js`, or keep it behind admin auth.
13. **Raw error text on upload finalize.** `api.model-upload.jsx:51` returns `e.message` to the merchant. Messages such as `invalid upload key: …` and `upload … exceeds …` are developer wording. Map the tagged codes to merchant copy, as the register-model route already does.
14. **Spoofable setup signal.** `api.tryon-installed` is unauthenticated, so anyone can flip a product to "Live" in the merchant's admin. It's low impact (admin status only), but worth folding into the App Proxy work in #5.
15. **Hard-coded dialog label.** The theme dialog's `aria-label` is "Sunglasses virtual try-on" (`tryon_button.liquid:50`). It's hard-coded and not localized; use the product title or a locale string.
16. **Owner shop hard-coded.** `FREE_ACCESS_SHOPS` defaults to the owner's store in source (`billing.server.js:17`). Move it to environment configuration only, so a fork or a staging deploy doesn't comp that shop by accident.
17. **Repository weight.** About 20 MB of the owner's brand models are committed and publicly served under `/tryon/models`, alongside a `.blend` file and renders at the root. Once #2 removes the storefront fallback, the bundled demo frames are only needed for local development.
18. **Stale compliance comment.** `webhooks.customers.data_request.jsx` lists "the only tables" as of 2026-07-22. `ShopSubscription` has been added since (still no shopper data); refresh the verification note.

## Suggested order of work

1. **#1 and #2.** Shoppers see these, and they undermine trust in the core feature. Both are small changes in the theme block and `main.js`.
2. **#3 and #4.** App Review and privacy exposure; mostly configuration and copy.
3. **#8.** CI first, so everything after it is protected.
4. **#5, #6 and #7.** Hardening the public endpoints.
5. **#9, #10 and #11**, then the P3 items.

Fixing #1–#4 would lift privacy and the storefront experience to about 3/4 each, taking the total to about 18/24. #5–#11 are what get the remaining areas to 4.
